# Plan 候选池联调版

版本：`2026-11-01-plan-pool-2`

## 部署

1. 打开同目录 `travel-companion.mjs`，复制完整代码。
2. 在现有 Cloudflare Worker 的“编辑代码”中整体替换后部署。保留现有 Secrets：`DEEPSEEK_API_KEY`、`AMAP_WEB_KEY`，以及原有的模型、访问码和来源配置。
3. 打开现有 Worker 的 `/api/health`，确认 `version` 为本版本、`candidatePoolContract: 2`、`poiQueryPlanning: true`、`amapKeyConfigured: true`。
4. 刷新 GitHub Pages 前端，从 Plan 开始测试。只更新前端时，页面会保留草案并提示后台版本不匹配，不会把旧 POI 当作已筛选推荐。

## 贵阳验收

- 起点、终点填贵阳，城市填贵阳，天数填 3，日期留空。
- 先选“历史文化＋古建筑”，补充“不喜欢商业化，想了解当地历史”；生成后检查地点组合、推荐理由和适合出行的时间段。
- 另生成一轮“自然风光＋摄影打卡”，保持其余条件一致，比较实际地点、停留和推荐理由。保留真正相关的重叠点，不要求为了不同而强行换景点。
- 首个国内城市会自动发现候选并尝试细化 Plan；其他城市按需点“发现这个城市的候选”。每城最多 6 次地图查询，另有 DS 检索策划与 Plan 调整调用，因此比旧 POI 实验更慢。
- 在城市备选点＋，再点“按选择调整 Plan”。地点应进入新方案并保留旧版本；点－后不得继续选入，候选本身不删除。锁定地点丢失、重复或身份错误时拒绝覆盖原方案。
- 验证刷新页面后候选与选择仍保留。浏览器本地保存，不是跨设备同步。

## 当前边界

- 此版只自动为国家标记为中国的城市接入高德候选。国外城市保留 AI 草案，未宣称地点或路线已核验。
- 搜索命中属于来源线索，不是兴趣评估、热榜或官方认证。此版未接小红书站内热榜。
- DS 使用候选名称、类别、位置与偏好做初筛和排程，地点背景的证据仍有限，不能把生成理由当成已证实的历史介绍。
- 只核对地点身份与坐标。门票、开放、营业、预约及按日期复查未自动完成；真实道路路线矩阵与住宿检索也未接入。
- AI 更新当前城市时，从多组查询均衡抽取至多 30 个普通候选参与评估；用户明确选择与当前选中候选额外保留，不因抽样丢弃。完整搜索候选保留在界面中可加回。
- 用户把超出时间容量的多个点都设为必去时，当前要求 DS 提出取舍；身份与保留约束是硬校验，时间可行性仍是模型判断，不能称为已算出可行路线。

## 已完成验证

`node --test tests/plan-pool.test.mjs`：8 项测试（模拟外部接口），覆盖偏好传入、差异查询、降级、候选去重、身份校验、必去/排除约束、候选抽样与加减状态。
浏览器以独立模拟夹具验证了展开候选、加入、移除、锁定保留和历史版本。模拟夹具不发布。
真实 DS/高德推荐质量需要部署后验收，当前未宣称通过。

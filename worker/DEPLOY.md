# Plan 精选与行程展示版

版本：`2026-11-01-plan-curation-3`，候选协议版本 `3`。

## 部署与继续测试

1. 将同目录 `travel-companion.mjs` 全部复制，整体替换现有 Cloudflare Worker 代码并部署；原有 Secrets 与环境配置保留。
2. `/api/health` 应出现 `version: "2026-11-01-plan-curation-3"` 和 `candidatePoolContract: 3`。
3. 强制刷新前端。之前的旅行需求和方案仍在本浏览器保存。点击“修改旅行需求”，按原需求重新生成，即可让每个国内城市完成新筛选；也可逐城在备选中重试。旧候选没有 AI 精选结果时，不会按原始搜索顺序展示。
4. 继续自由输入目的地，不针对长沙、衡阳或其他城市预设答案。

## 这一版修正

- 检索策划使用与 Plan 相同的 `thinking: disabled` 配置，增加时限与安全错误诊断。上一轮降级原因仍需查看实际服务日志确认，不能把参数修正当作已经证明的根因。
- 独立的 DS 筛选步骤读取全部有效候选，按明确偏好、兴趣关系、代表性、体验互补与地理分区做取舍；排除入口/停车场/同质分店等噪声。最多保留12个，数量少时不凑数。
- 这是模型按规则作出的可解释排序，不是训练好的固定评分模型、热榜或已验证的最优路线。后续以盲测反馈调整规则。
- 前台每城默认展示最多6个普通备选，已经安排的地点在当天展示；待加入的明确选择额外保留。其余精选可换一组查看；原始候选保留在会话数据中，不直接堆到页面。
- 为每个国内城市逐一发现并筛选，再统一细化 Plan。任何城市失败明确保留草案/重试状态，不声称已完成筛选。
- 拒绝“历史人文地点”“地方生活街区”“特色餐饮区域”等占位行程。明确的交通、抵达或休息日可没有游览点。
- 每天的具体景点与推荐理由直接展示；当地风味和可选餐饮写当天 `local_food`，不强制每餐时刻。具体店铺必须匹配候选，未核验的菜品/区域建议明确标注。
- 生成后收起需求表单；核验、来源、交通、资料上传与示例工具折叠，保留主要的行程和调整操作。

## 验收重点

- 多城市行程中，每个国内城市都完成候选筛选，具体游览日有具体地点。
- 不再出现98条原始搜索结果；少量备选有推荐理由与取舍，不把搜索位置当推荐名次。
- 改兴趣/文字喜好后，观察地点组合与推荐理由是否合理变化；允许真正相关的重叠地点。
- ＋可将备选加入当天，餐饮加入 `local_food`；－排除后仍可撤销；锁定地点丢失、身份错误或重复时拒绝覆盖旧方案。
- 未加载新协议、精选失败和未知动态信息均应明确显示状态。

## 验证与边界

13项自动检查通过，外部接口使用模拟数据；浏览器模拟98个原始候选检查精选展示、当地风味进入每日卡片及餐饮加回流程。模拟夹具不发布。

真实 DS/高德效果待部署后测试。门票、开放时间、预约、真实道路路线及国外地图能力仍未接通完整核验。推荐名额、排除规则与多样性策略属于首版可调规则，不能据此宣称真实推荐质量已达标。
